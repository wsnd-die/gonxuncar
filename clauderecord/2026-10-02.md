#### V1.20.4 - 2026-10-02
- **修改类型**：修复（**MSP 帧解析器与发送端格式完全对不上，颜色恒为兜底值**）
- **涉及模块**：
  - 硬件驱动层 / `hardware/sensors/msp_color.c`
  - 硬件驱动层 / `hardware/sensors/msp_color.h`
- **修改内容**：

  **现象**：MSP 颜色永远取不到，`app/block_collect.c` 每次都落到
  `collect_default_color()`（槽 2/3 = 红、槽 4/5 = 蓝）那个兜底值。

  **根因有两层，第二层才是致命的**：

  1. **解析器对不上实际帧格式**。发送端是
     `sprintf(tx_buf, "A3%s%d%d%dB3\r\n", color, r, g, b)`，
     线上是 `A 3 r 2 0 0 3 0 4 0 B 3 \r \n` 这种**变长**流；而 V1.20.0 的解析器
     按定长 7 字节二进制帧 `A 3 R G B B 3` 写的，`rx_idx==7` 时查
     `ch[5]=='B' && ch[6]=='3'` —— 实际到第 7 个字节时 `ch[5]` 是数字，**每帧都被拒**，
     `rx_ok` 恒为 0。
  2. `MSP_CharToColor()` 读的 `s_msp.color` **从来没有被赋值过**（全文件只有两处读、
     零处写），即使帧拼出来了也返回 `COLOR_UNKNOWN`。解析器实际填的是
     `gy33_r/g/b`，而那两个字段没有任何读者。

  **改法**：

  - 状态机按真实帧重写，只认帧头与颜色字符：
    `WAIT_A →('A')→ WAIT_3 →('3')→ COLOR → TAIL`。
    进入 `COLOR` 时**帧头后第一个字节就是颜色字符**（发送端 `%s` 的 `'r'`/`'b'`），
    直接存进 `s_msp.color` 并置 `pending`；`TAIL` 里丢弃数字段与帧尾，遇 `'A'` 重新对齐。
  - `WAIT_3` 里遇到 `'A'` 停在原状态（它就是新帧头的第一字节），遇其它字符才回 `WAIT_A` ——
    否则 `A A 3 ...` 这种流会漏掉一帧。
  - **颜色从字符直接取，不用 `Color_Judge()`** —— 颜色字符本身就在流里，
    比从 RGB 反推可靠得多。
  - **RGB 三个字段整个删掉**。发送端 `%d%d%d` 没有分隔符也没有定宽，
    "2003040" 既可能是 (200,30,40) 也可能是 (20,03,040)，**原理上切不开**。
    要用 RGB 必须先改发送端为 `%03d%03d%03d` 或加分隔符。
  - 删除 `MSP_RX_WAIT_B`（枚举里从没被用过）、`ch[8]`、`rx_idx`、`color_fresh`
    （都是死字段）。
  - `MSP_Color_Take()` 取到色时打印一行 `[MSP] color='r' -> RED`（任务上下文，
    不是 ISR）。同时改成**先把字符取到局部再清 `pending`**，避免 ISR 在两步之间
    把 `color` 换成下一帧。
  - `MSP_Color_GetDiag()` 增加 `rx_ok` 出参（原签名 3 个参数且**零调用者**，
    改动无影响）。`rx_ok == 0` 是「一帧都没拼出来」的直接判据。
  - 诊断计数器加 `volatile`（ISR 写、任务读）。
  - `.h` 文件头注释重写成真实帧格式（原注释还写着「收 'r'/'b' 一个字符」）。

- **影响范围**：仅 MSP 取色路径。`MSP_Color_Wait()` 的签名与语义未变，
  `app/block_collect.c` 一行不用改。**帧格式里的数字段现在被丢弃**，
  将来要用 RGB 需要同时改发送端。
- **验证状态**：**编译已验证**（`cmake --build --preset Debug --clean-first` 通过，
  无未定义符号，`Color_ToString` 已链接）。**实机未验证** —— 未确认能否真正解出颜色。
- **备注**：
  1. 上机先看串口有没有 `[MSP] color='r' -> RED` 这种行。没有就调
     `MSP_Color_GetDiag()` 看 `rx_ok`：`rx_ok==0` 说明帧头都没对上（接线/波特率/
     发送端格式），`rx_ok>0` 而取不到色说明是调用时机的问题。
  2. ⚠ 发送端把 `$` 去掉后帧尾是 `B3`。当前解析器**不校验帧尾**（只靠 `'A'` 重新对齐），
     所以帧尾长什么样都行；但如果将来要在数字段里取 RGB，就必须校验。
  3. USART2 波特率固定 115200（改要动 `.ioc`），MSP 侧必须匹配。

#### V1.20.5 - 2026-10-02
- **修改类型**：修改（初始化调用点归位；**顺带修掉一处重复调用**）
- **涉及模块**：
  - Core / `Core/Src/main.c`（接管调用）
  - Core / `Core/Src/usart.c`（撤出调用）
  - Core / `Core/Src/app_freertos.c`（撤出调用）
- **修改内容**：

  **背景**：`MSP_Color_Init()` 此前被**调用两次** —— V1.20.0 加在
  `Core/Src/usart.c` 的 `USER CODE BEGIN USART2_Init 2`，之后又被加了一份到
  `Core/Src/app_freertos.c` 的 `USER CODE BEGIN Init`（`IR_Init()` 旁边）。
  两处都在 USER CODE 区，CubeMX 重新生成不会冲掉，所以一直并存。

  这不是纯冗余，是有害的：`MX_USART2_UART_Init()`（main.c:108）先跑，
  第一次 `MSP_Color_Init()` 已经挂上 DMA；等 `MX_FREERTOS_Init()`（main.c:120）
  跑第二次时，函数体是 `memset(&s_msp, 0, ...)` 然后
  `HAL_UARTEx_ReceiveToIdle_DMA()` —— **DMA 还挂着，这个调用返回 `HAL_BUSY`
  直接退出**。净效果是解析状态被清零、而接收没有重挂。功能上看不出问题
  （第一次挂的还在），但属于随时会咬人的脆弱点。

  **改法**：按用户要求把初始化统一放到**主函数**里。

  - `Core/Src/main.c`：在 `/* USER CODE BEGIN 2 */`（所有外设初始化之后、
    `osKernelStart()` 之前，与已有的 `fdcan2_UserInit()` 并列）调
    `MSP_Color_Init();`，并在 `USER CODE BEGIN Includes` 里加
    `#include "msp_color.h"`。这是 CubeMX 保留区，重新生成不会丢。
  - `Core/Src/usart.c`：撤掉 `USER CODE BEGIN USART2_Init 2` 里的调用，
    留一句注释指路。**`#include "msp_color.h"` 保留** —— 那个文件里的
    `HAL_UARTEx_RxEventCallback` 分发器仍要调 `msp_color_RxEventCallback`。
  - `Core/Src/app_freertos.c`：撤掉那份重复调用，注释指路。

- **影响范围**：`MSP_Color_Init()` 现在**全工程只有一个调用点**（main.c）。
  接收挂载时机不变（仍在 `MX_USART2_UART_Init()` 之后），行为一致。
- **验证状态**：**编译已验证**（`cmake --build --preset Debug --clean-first` 通过，
  无未定义符号，无新增告警）。**实机未验证**。
- **备注**：`MSP_Color_Init()` 是在 RTOS 启动前调的，此时 DMA/UART 中断已经使能，
  第一个字节可能在 `osKernelStart()` 之前就进 `msp_color_RxEventCallback` ——
  那只是在中断里写几个变量，安全。

#### V1.20.7 - 2026-10-02
- **修改类型**：新增（**临时调试**：把 MSP 收到的原始帧打出来）
- **涉及模块**：
  - 硬件驱动层 / `hardware/sensors/msp_color.c`、`.h`
  - Core / `Core/Src/app_freertos.c`（`gripper_task` 循环里挂调用）
- **修改内容**：

  **背景**：串口上看不到 `[MSP] color='r' -> RED`。但 V1.20.4 里那句打印位于
  `MSP_Color_Take()` 成功解码之后 —— 收不到帧、或帧解码失败，都是一个字不打，
  所以「没打印」无法区分「没收到」和「收到了但没解出来」。用户要求直接看原始内容。

  - 解析状态机的最后一档由 `MSP_RX_TAIL`（丢弃数字段）改成 **`MSP_RX_DIGITS`**：
    把颜色字符后面的数字**原样收进 `s_msp.digits[]`**（上限 `MSP_DIGITS_MAX = 16`，
    超长截断不报错），遇非数字字节即认为整帧结束，置 `frame_ready`。
    颜色字符也不再要求必须是 `'r'`/`'b'` —— 不是也照收，留给调试看。
  - 新增 **`MSP_Color_DebugPoll()`**：有新整帧就打印一行
    `[MSP-RX] color='r' rgb_raw="2003040"`，**任务上下文**（不在中断里 printf）。
    从 volatile 数组先拷到本地缓冲再 printf，避免读到 ISR 正在写的半截。
  - `gripper_task` 的 `for(;;)` 里在 `BlockCollect_Poll()` 之后调
    `MSP_Color_DebugPoll()`，与采集流程**解耦** —— 不管采集跑没跑、按键按没按，
    只要 USART2 收到帧就会打。
  - 保留 `MSP_Color_Take()` 里那句 `[MSP] color='r' -> RED`（那是「被采集消费」
    的路径），两行前缀不同可区分。

- **影响范围**：仅新增调试输出。解析结果、`pending` 语义、`MSP_Color_Wait()`
  行为均未变 —— 数字段依旧**不参与**颜色判定（`%d%d%d` 无分隔符无定宽，
  原理上切不开），只做原样展示。
- **验证状态**：**编译已验证**（`cmake --build --preset Debug --clean-first` 通过，
  无未定义符号，`MSP_Color_DebugPoll` 已链接）。**实机未验证**。
- **备注**：
  1. 连 `[MSP-RX]` 都不出现 ⇒ USART2 一个字节都没进来（接线 / 波特率 115200 /
     MSP 没发）；可以再配合 `MSP_Color_GetDiag()` 的 `bytes` 计数确认。
  2. 有 `[MSP-RX]` 但 `rgb_raw` 长度不对 ⇒ 发送端格式与预期不符。
  3. 确认收帧正常后，`gripper_task` 里那行调用与 `MSP_Color_DebugPoll()` 本身
     都可以摘掉。

#### V1.21.0 - 2026-10-02
- **修改类型**：新增（奖杯名次判断接入；**兼容升级** —— 只在 `TT_t` 已有字段上补访问器）
- **涉及模块**：
  - 应用层 / `app/block_collect.c`、`.h`（奖杯分支补名次判断）
  - 应用层 / `app/ColorIdentif.c`、`.h`（`trophy[]` 补访问器）
  - Core / `Core/Src/app_freertos.c`（`FC_TASK` 摘掉抢帧的调试打印）
- **修改内容**：

  **背景**：NX 奖杯链路已通（`NX_GetTrophyRank()` 返回 `'1'`/`'2'`/`'3'`），
  但 `block_collect.c` 的奖杯分支只做「等 IR → 夹紧 → 转一步」，拿到的名次没人用；
  `g_tt.trophy[3]` 这个字段从 V1.1.0 起就存在，**一直是零读写**。

  **语义确认**（用户 2026-10-02）：NX 的 `'1'/'2'/'3'` 是**当前这一个奖杯的名次**，
  每收一个问一次；名次存 `g_tt.trophy[]`；名次→转盘工位的映射沿用
  `worker_task.c` 现有的 `NF_TROPHY_SLOT[]`（冠军→3、亚军→2、季军→1），不另建一套。

  - `ColorIdentif.c/.h`：新增 `TT_SetTrophy(slot, rank)` / `TrophyAtSlot(slot)`，
    下标 0~2 对应转盘物理槽 1~3，越界直接拒绝。取值 1=冠军 2=亚军 3=季军，
    与 `Jang_type` 同编码，所以 NX 的字符 `'1'`~`'3'` 减 `'0'` 即可。
  - `block_collect.c`：新增 `wait_trophy_rank(rank_out, timeout_ms)` —— 轮询
    `NX_GetTrophyRank()`，只接受 `'1'`~`'3'`，其余当脏数据丢掉继续等，
    超时（新增常量 `TROPHY_RANK_TIMEOUT_MS = 3000`，★实测）返回 false。
    奖杯分支在 `BlockBasic_GripperClamp()` 之后调它，成功则
    `TT_SetTrophy(slot-1, rank)` 并打印 `[COLLECT] trophy slot=N rank=R`。
  - 奖杯分支顺带对齐了物料分支的写法：夹紧后加 `osDelay(COLLECT_SETTLE_MS)`；
    单槽超时由原来的 `return`（放弃整轮）改成 `continue`（跳过该槽）；
    超时日志由误抄的 `no cone, abort` 改成 `trophy slot N: no block, skip`。

  **⚠ 关键副作用**：`NX_GetTrophyRank()` 是**消费式**的（读后清 `trophy_fresh`）。
  `FC_TASK` 里原本每 ~110ms 调一次并 printf，会把帧抢走 —— 采集侧基本永远拿不到。
  已把那两行摘掉，原地留注释说明原因与重新打开的注意事项。
  **现在 `NX_GetTrophyRank()` 全工程只有 `wait_trophy_rank()` 一个调用点。**

- **影响范围**：
  - 奖杯分支现在会**阻塞等待名次**，单槽最多多花 `TROPHY_RANK_TIMEOUT_MS`。
  - `FC_TASK` 不再打印 `[NX] trophy=`。想调试请**临时**改，不要与采集并存。
  - 名次→工位的映射本次**未接** —— `NF_TROPHY_SLOT[]` 仍是摆放阶段自己查，
    `TrophyAtSlot()` 目前零调用者（会被 `--gc-sections` 回收）。
- **验证状态**：**编译已验证**（`cmake --build --preset Debug --clean-first` 通过，
  无未定义符号，`TT_SetTrophy` 已链接）。**实机未验证**。
- **备注**：
  1. 上机看 `[COLLECT] trophy slot=N rank=R` 的 R 是否 1/2/3。若一直是
     `rank timeout`，说明 NX 没在这个窗口里发帧 —— 要么 NX 侧时机不对，
     要么 `TROPHY_RANK_TIMEOUT_MS` 太短。
  2. `g_tt.trophy[]` 只在 `TT_Init()` 里被 `memset` 清零，每轮采集开头会重置。
  3. ⚠ 分支开关 `k` 仍是 `static volatile bool k = false`，**全工程没有任何地方
     给它赋值**。当前判断写的是 `if (k==false)` → **永远走物料分支**，本次新加的
     奖杯分支是死代码。要跑奖杯必须先给 `k` 一个来源（按键 / 流程阶段 / 编译期宏）。

#### V1.21.1 - 2026-10-02
- **修改类型**：修改（**不兼容** —— 摆放阶段的「名次 → 转盘槽位」改走反查，删除旧表）
- **涉及模块**：
  - 应用层 / `app/ColorIdentif.c`、`.h`（新增反查函数）
  - 应用层 / `app/worker_task.c`（`NF_Stage_PlaceDown` 改用反查；删除 `NF_TROPHY_SLOT[]`）
- **修改内容**：

  **问题**：V1.21.0 把名次存成了 `g_tt.trophy[槽位] = 名次`（**槽位 → 名次**），
  而摆放阶段用的 `NF_TROPHY_SLOT[rank]` 是**名次 → 固定工位**
  （冠军→3、亚军→2、季军→1）。方向相反，而且后者是**错的**：

  ```
  假设奖杯进来顺序是 亚军 → 冠军 → 季军
     槽1 = 亚军    槽2 = 冠军    槽3 = 季军
     g_tt.trophy[] = {2, 1, 3}

  摆放第一步要放亚军:
     旧代码  NF_TROPHY_SLOT[second_place] = 2 → 转到槽2 → 拿出来的是**冠军** ❌
     新代码  反查 trophy[] 哪个槽存了 2 → 槽1 → 转到槽1 ✓
  ```

  `NF_TROPHY_SLOT[]` 是旧 QR 方案的遗产 —— 那时 QR 码直接告诉你"冠军在哪个工位"，
  所以可以做固定表。现在槽位由**收集顺序**决定（第 N 个进槽 N），名次是收完才填的，
  固定表不再成立。**摆放顺序本身（先亚后冠再季）没有改，`NF_RANK[]` 原样不动。**

  - `ColorIdentif.c/.h`：新增 `SlotByTrophy(uint8_t rank)` —— 扫 `g_tt.trophy[0..2]`
    找哪个槽存了该名次，返回 g_tt 下标 0~2，没找到返回 `SLOT_NONE`。
    命名与返回约定都对齐现有的 `SlotByColor()`（0 基下标 + `SLOT_NONE`）。
  - `worker_task.c` 的 `NF_Stage_PlaceDown()`：
    `slot = NF_TROPHY_SLOT[rank]` 换成 `slot_idx = SlotByTrophy(rank)`，
    转盘参数 `BlockBasic_TurntableTo(tslot)` 由 `slot_idx + 1` 得来
    （g_tt 下标 0~2 → 转盘物理槽 1~3，与 `TT_RotateByQR` 的 `slot + 1` 同约定）。
    `SLOT_NONE` 时**不猜**：打印 `[FLOW] PlaceDown rank=N 在 g_tt.trophy[] 里找不到, 跳过`
    并跳过本拍（`s_place_idx++` 后请求下一阶段），避免转到不相干的槽去放。
    末尾的 `done` 日志改成打印 `tslot`。
  - 删除 `NF_TROPHY_SLOT[]`（已无引用；留着会被 `-Wunused-const-variable` 警告，
    而且会诱导后来者继续用这张错表），原地留注释说明为何删除。

- **影响范围**：
  - 摆放阶段现在**依赖采集阶段先跑过**并有正确的 `g_tt.trophy[]`。采集没跑、
    `k` 没打开、或 NX 超时导致名次未定，`SlotByTrophy()` 都会返回 `SLOT_NONE`，

#### V1.21.2 - 2026-10-02

- **涉及模块**：

- **修改内容**：

  **背景**：V1.21.0 的取法是「夹紧之后再 `wait_trophy_rank()` 等一帧」。问题有两个：
  名次要到夹住之后才定，而用户希望**夹住之前就判好**；而且只认一帧，

  **改法**（用户 2026-10-02 提出）：在**物块完全进来之前那段时间**对 NX 报的名次
  做简单投票，票多者胜，夹住之前定好。

  投票窗口天然就是「等 IR 触发」的那段等待，所以直接并进 `wait_block_entered()`：

  ```c
  static bool wait_block_entered(uint32_t timeout_ms, uint8_t *rank_out);
  ```

  - `rank_out == NULL` → 原有行为（物料分支用，不关心名次）。
  - `rank_out != NULL` → 等待期间把 `NX_GetTrophyRank()` 收到的 `'1'`~`'3'`
    累计进 `votes[1..3]`；`IR_ObjectEntered()` 成立时取票最多者写入 `*rank_out`
    （**一票都没有时写 0**，表示名次未定），并打印一行票数明细：
    `[COLLECT] trophy votes 1:3 2:0 3:1 -> rank=1`。

    不清掉会被算进这一轮的票。

  - 删除 `wait_trophy_rank()`（已无调用者）与 `TROPHY_RANK_TIMEOUT_MS`
    （投票窗口现在就是 `COLLECT_IR_TIMEOUT_MS`，不再需要单独的等待上限）。

  奖杯分支相应改成「等进来（带投票）→ 定名次存 `g_tt.trophy[]` → 再夹紧」：

  ```c
  uint8_t rank = 0u;
  if (!wait_block_entered(COLLECT_IR_TIMEOUT_MS, &rank)) { ...; continue; }
  if (rank != 0u) { TT_SetTrophy(slot - 1u, rank); ... }

  (void)BlockBasic_GripperClamp(slot);
  ```

  `SlotByTrophy()` 反查、摆放阶段均未动。物料分支传 `NULL`，行为与之前完全一致。
- **验证状态**：**编译已验证**（`cmake --build --preset Debug --clean-first` 通过，
  无未定义符号，`block_collect.c` 无告警）。**实机未验证。**
- **备注**：
  1. 投票窗口现在是**整个等待期**（转盘转到位 → 物块完全进来），可能长达数秒。
     若实测发现窗口前段混进了**上一个奖杯**的票，需要把窗口收窄
     （比如只统计 IR 触发前最后 N ms），届时再调。
  2. 票数明细那行 printf 是标定用的 —— 看两轮下来票数分布是否一边倒，

#### V1.22.0 - 2026-10-02
- **修改类型**：修复（`Place()` 的**坐标系错配** —— 车体量被当作世界系增量用）
- **涉及模块**：

- **修改内容**：

  **问题**：`Place()` 从圆心像素偏差算出的是**车体系**补量 ——
  `fwd` = 车头方向、`left` = 车体左方：

  ```c

  float left = -x * PLACE_CIRCLE_SCALE_M;
  Nav_MoveBody(fwd, left, 0);      /* ← 但 Nav_MoveBody 收的是世界系增量 */
  ```

  而 `Nav_MoveBody()` 的实现（`NavigationMecanum.c:244`）是
  `目标 = Self_Dir + (target_x, target_y, target_yaw)` —— 它在**世界系**里叠加。
  `Self_Dir` 本身没问题（`Nav_GoToWorld` 每次到位都会把它刷成实测位姿，
  所以"在当前位置基础上移动"这一层是做到了），错的是**参考系**：
  把车体量当世界系用，只有车头正好朝世界 +X 轴（yaw=0）时才等价。

  **改法**（用户 2026-10-02 确认走导航闭环 + 修坐标系）：按当前航向把
  车体量转成世界系增量再交给 `Nav_MoveBody()`：

  ```c
  float c = cosf(Self_Dir.yaw);
  float s = sinf(Self_Dir.yaw);
  Nav_MoveBody(fwd * c - left * s,
               fwd * s + left * c, 0.0f);
  ```

  旋转矩阵与 `Nav_GoToWorld()` 里那段「世界 → 车体」
  （`bvx = vx*c + vy*s; bvy = -vx*s + vy*c`，`NavigationMecanum.c:144-146`）
  **互逆**，两处对得上。

  后退那一步（`Nav_MoveBody(-0.05, 0, 0)`）同样转一次；因为前面一次移动到位后
  `Self_Dir.yaw` 已被刷新，所以**重新取一次 `c`/`s`** 再用。

  同时删掉 `Place()` 里两段注释掉的 `Mecanum_CalculateMove/ExecuteMove`
  （那是"车体系直驱、不走导航"的旧方案，与本次选定的方案互斥，
  留着只会误导；需要的话可从 git 历史取回）。

- **影响范围**：所有调用 `Place('O', ...)` 的地方 —— `NF_Stage_FindCircle`
  和 `NF_Stage_PlaceDown`。**车头不朝世界 +X 轴时行为会明显改变**（那正是原来错的情况）。
  朝 +X 轴时行为不变（`c=1, s=0`，退化回原式）。
- **验证状态**：**编译已验证**（`cmake --build --preset Debug --clean-first` 通过，
  无未定义符号，`block_basic.c` 无告警）。**实机未验证。**
- **备注**：
  1. `Self_Dir.yaw` 是**弧度**（与 `Nav_GoToWorld` 里 `cosf(pose.yaw)` 同量纲），
     别误当角度。
  2. `0.068f`（基础前移量）与 `PLACE_CIRCLE_SCALE_M`（像素→米）仍是**未标定值**，
     本次未动。
  3. 与 `CLAUDE.md §2` 里「`Nav_MoveBody()` 实为世界系增量而非文档所称车体量」

  - `block_basic.c` 的 `Place()`：两处调用的常量由 `PLACE_MOVE_WAIT_MS`(800)
    换成 `PLACE_MOVE_TIMEOUT_MS`(1500)，并检查返回值，超时打印
    `[PLACE] 前移/后退 没等齐到位 (超时)`。

- **影响范围**：`Place()` 的两段移动。正常情况比原来**更快**（走完就返回，
  不用等满固定时间）；异常情况比原来**更慢**（要等满超时）。
- **验证状态**：**编译已验证**（`cmake --build --preset Debug --clean-first` 通过，
  无未定义符号，`Emm_V5_Is_Reached` / `Mecanum_MoveBodyPos` 均已链接，
  两个文件无告警）。**实机未验证。**
- **备注**：
  1. ⚠ `MEC_POS_START_DELAY_MS` 太短会误判（读到上一次的残留标志）、太长则白等。
     若实测发现"指令发出去了但函数立刻返回、车还没动"，就是它太短。
  2. ⚠ 查一轮四个轮子最坏 200ms（每个 50ms 超时）。**电机掉线时每一轮都是 200ms**，
     直到 `PLACE_MOVE_TIMEOUT_MS` 用完才返回 false —— 这是有意的，不是卡死。
  3. 到位标志**只在位置模式（相对运动 raF=0）下有意义**；若改用绝对位置、
     或电机被堵转，标志行为会不一样。堵转时永远等不到到位，只能靠超时退场。
  4. 仍然**不是闭环** —— 位置模式给脉冲数、到位标志判"走完了"，但走歪了不修正。

- **修改内容**：

  **背景**：此前 `NF_Stage_Collect()` 会**阻塞轮询 `BlockCollect_IsDone()` 最长 120 秒**，
  而采集本身又在 `gripper_task` 里同步跑完整轮 —— 于是"收集完才开导航"。
  用户要求：**一直往前导航，物块/奖杯在途中收**。

  **关键事实**：采集侧**完全不碰驱动电机**（只用 UART5 舵机总线、IR 引脚、
  USART2 的 MSP、UART4 的 NX），所以它和导航本来就能并行 —— 真正卡住的只是那个等待循环。

  **四件事**：

  1. **`NF_Stage_Collect()` 非阻塞**（`worker_task.c`）：删掉整个等待循环与
     `NF_COLLECT_TIMEOUT_MS`，只做 `SetStage/Reset/Start` 然后立刻
     `NLF_Request(Event_Navigation)`。`BlockCollect_IsRunning()/IsDone()` **保留**
     （改成查询式，流程不再等）。
  2. **跨任务打断标志 `g_route_abort`**（`worker_task.c` 定义 / `worker_task.h` 声明）：
     `gripper_task` 在 `wait_block_entered()` 里 IR 进料时调 `Route_AbortRequest()`；
     `Nav_GoToWorld()` / `Arc_Run()` 在自己的轮询循环里读到就**停车、清零、提前收尾**。
     - **刻意不用 `NLF_Request()`**：打断发生时 NLF_TASK 正阻塞在导航循环的
       `osDelay()` 里、根本不在 `osThreadFlagsWait` 上，线程标志毫无作用；而且会把
       `NLF_FLAG_RUN` 留成置位，等当前 `NLF_RunFlow` 返回后**多跑一次流程**。
     - 单核 M4 上单字节 volatile 读写天然原子，不加临界区。
     - 语义是**电平不是队列** → 没人消费时会残留。所以 `NF_Stage_GoHome()` 开头
       显式清零，否则回家路线（`Nav_RunWaypoints` 走 17 点）第一拍就被打断。
  3. **`Nav_GoToWorld()` 可被打断**（`NavigationMecanum.c`）：主循环里查标志，
     打断时 `NAV_Stop()` + 刷新 `Self_Dir` + 置 `s_nav_aborted` + `return false`。
     返回值**保持 `bool`**（改返回类型要动 `Nav_MoveBody`/`Nav_RunWaypoints`/头文件三处，
     不符合"简洁"），用新增的 `Nav_LastAborted()` 区分"超时"和"被打断"。
     **`Nav_FeDuanPoint()` 的游标在被打断时照推**（用户要的是"改奔下一个点"，
     不是重试当前点）；只有**超时**才不推进。
  4. **路线源可编译期切换**（`worker_task.c`）：新增 `NF_ROUTE_ARC`（默认 0）。
     - 0 = 分点导航，`NF_RouteStep()` 内部就是原来的 `Nav_FeDuanPoint()`。
     - 1 = 圆弧模式：那 8 个点位**整个不导航**，改成 `NF_ARC_ROUTE[]` 那张 4 段表
       逐段执行 —— `导航到物料弧起点 → 跑物料弧 → 导航到奖杯弧起点 → 跑奖杯弧`。
       物料弧替代 `g_waypoints[]` 下标 6~10 的 e/c/d/a/b；奖杯弧替代下标 0~2 的
       奖杯二维码点/亚军点/亚军点。
     - `NF_Stage_Navigation()` 里那一句由 `Nav_FeDuanPoint()` 换成 `NF_RouteStep()`，
       **除此之外一字未改**；`NF_STAGES[]` 也一字未动。
     - 宏带 `#ifndef` 守卫，可从构建系统传 `-DNF_ROUTE_ARC=1` 覆盖。

  **`Arc_Run()` 同样可被打断**：主循环里消费 `g_route_abort`，走**正常收尾**
  （仍然 `return true`）—— 不借它的 `false`，那是留给"参数非法"的。
