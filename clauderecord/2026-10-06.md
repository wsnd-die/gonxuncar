#### V1.26.3 - 2026-10-06
- **修改类型**：修复（**物料放置永远只放同一个转盘槽**）+ 修复（`TT_SeekBlock()` 数组越界与槽号差一位）
- **涉及模块**：
  - 业务层 / `app/ColorIdentif.c`（`TT_SeekBlock()`）
  - 应用层 / `app/worker_task.c`（`NF_Stage_FindCircle()`）
- **修改内容**：

  **现象**：物料放置永远落在同一个转盘槽上，与物块颜色/形状完全无关。

  **根因（`worker_task.c`）**：`NF_Stage_FindCircle()` 里是

  ```c
  while (TT_RotateByQR()) { }                 /* 把整圈抽干 */
  Place('O', ..., TT_CurrentSlot());          /* 只放这一格 */
  ```

  `TT_RotateByQR()` 内部本来就是**每次只走一格**（`TT_SeekBlock()` 推进
  `s_seek_slot`），`while` 把游标一路推到 4 → **整圈转完只在最后一格放一次**；
  再 `TT_RotateReset()` 就变成每轮重复同样的序列。

  **修法**：`while` → `if`，一次 FindCircle 只转一格、放一格。游标由
  `NF_FlowSeed()` 里那句 `TT_RotateReset()` 清零，跨 5 次 FindCircle 自然递增
  （第 0 次 = 圆锥槽 1，之后 4 件按 `T1[]` 的 (颜色, 形状) 查找）。

  **根因（`ColorIdentif.c`）**：`TT_SeekBlock()` 的查找循环

  ```c
  for (uint8_t i = 2; i <= 5; i++) {
      if (g_tt.color[i]==T1[s_seek_slot-1][0] && g_tt.shape[i]==T1[s_seek_slot-1][1]) {
          s_seek_slot++; return i;
      }
  }
  ```

  两个错：
  1. **数组越界** —— `g_tt.color[]` / `g_tt.shape[]` 都是 5 元素（下标 0~4），
     `i = 5` 时读到后面紧跟的 `trophy[0]`。
  2. **槽号差一位** —— `i` 既当 g_tt 下标又当返回值，而 `g_tt.color[i]` 是
     **物理槽 i+1** 的颜色（采集侧 `identify_slot()` 写的是 `slot-1`）。

  改为按下标 `s = 1..4`（对应物理槽 2~5）扫描、返回 `s + 1`：

  ```c
  for (uint8_t s = 1u; s <= 4u; s++) {
      if (g_tt.color[s]==T1[s_seek_slot-1][0] && g_tt.shape[s]==T1[s_seek_slot-1][1]) {
          s_seek_slot++;
          return (uint8_t)(s + 1u);   /* 下标 → 物理槽 */
      }
  }
  ```

  下标从 1 起是因为**下标 0 = 物理槽 1 = 圆锥位**，采集从不写它。

- **影响范围**：物料摆放路径（仅此）。奖杯路径未动。`TT_SeekBlock()` 的返回值
  语义不变（物理槽号 1~5 / 0 = 没找到），只是算得对了。
- **验证状态**：编译已验证（clean build，`-Wall` 零告警）；**实机未验证**。
- **备注**：
  1. **本次没有新增任何表/函数。** 最初另起了一套 `NF_PLACE_ORDER[]` +
     `SlotByColorShape()`，发现与用户同期写的 `TT_SeekBlock()`（用 `T1[4][2]`）
     **功能重复**，已整段撤掉，只留上面两处修复 —— 摆放序的唯一来源是
     `ColorIdentif.c` 的 `T1[4][2]`。
  2. ⚠ **`NF_Stage_Collect()` 两个分支都 `NLF_Request(Event_Collect_L)`**
     —— 奖杯分支也是。这会让流程 `Collect_L` → `Collect_L` → … **无限循环**，
     FindCircle 一次都跑不到。原值是 `Event_Navigation` / `Event_NavCircleL`。
     **本次未改**，待用户确认为笔误还是有意。
  3. ⚠ **`NF_FlowSeed()` 的 g_tt 下标可能差一位**：那里是
     `for (s = 0; s < NF_TASK1_SLOT_COUNT-1; s++) TT_SetColor(s, …)` → 写
     g_tt 下标 **0~3**；而采集侧写的是下标 **1~4**。下标 0 物理上是槽 1（圆锥）。
     走 seed（不跑真实采集）时 `T1[]` 里会有一项匹配到下标 0 → 反查出物理槽 1。
     **本次未改**（该循环用户正在改）；真实采集路径不受影响。
  4. 单点导航与 FindCircle 的**对齐未验证**：5 次 FindCircle 之间各走**一个**
     waypoint，`s_idx` 起点决定了这 5 次是否正好落在摆放点 e,d,c,a,b 上。
     已加 `[FLOW] FindCircle -> 转盘物理槽 N` 日志，上机对着 `[NAV] 第 N 点` 核。

#### V1.26.4 - 2026-10-06
- **修改类型**：新增（**奖杯名次排除法补全**）
- **涉及模块**：
  - 业务层 / `app/block_collect.c`（新增 `trophy_fill_missing()`；`collect_slots()`
    的奖杯分支**只多了末尾一行调用**）
- **修改内容**：

  **问题**：`collect_slots()` 的奖杯分支里，某槽 `wait_block_entered()` 的投票**一票都没有**
  时 `g_tt.trophy[]` 留 0 → `SlotByTrophy()` 返回 `SLOT_NONE` →
  `NF_Stage_PlaceDown()` 把那个名次的奖杯**整件跳过**（只打一行"在 g_tt.trophy[]
  里找不到"），奖杯就一直留在转盘上。

  **依据**：3 个奖杯的名次是 `{1 冠军, 2 亚军, 3 季军}` 的一个**排列** ——
  互不重复。所以 `g_tt.trophy[]` 里**恰好只有一个 0** 时，那个槽必是剩下的名次。
  这一条同时覆盖两种情形：前两个都识别成功 → 第三个直接得出；只成功一个 →
  把下一个也识别完，就变成"恰好缺一个"，同样得出。

  **实现（尽量精简）**：

  - `g_tt.trophy[s] == 0` **本身就是"该槽名次未定"**，所以不另立
    `entered_mask` / `known_mask` 之类掩码，也不传参 —— 直接扫 `g_tt`。
  - 循环体**一行未改**，只在 3 个槽都过完之后加一次 `trophy_fill_missing();`
    （必须出循环才谈得上"缺哪一个"）。
  - 函数体 `static void trophy_fill_missing(void)`，约 20 行，一次扫描做完三件事：
    找唯一的 0、收集已出现的名次、顺手查重复。

  **两条护栏**（不满足就**不补**，宁可留 0 也不把错数据送下游）：

  | 条件 | 动作 | 理由 |
  |---|---|---|
  | `trophy[]` 里有 ≥ 2 个 0 | `return` | 只知道"是剩下的两名之一"，分不清谁是谁 |
  | 已知名次出现重复 | `return` | 名次是排列，撞了就说明视觉给错，"剩下的那个"不存在 |

- **影响范围**：奖杯采集分支。`TT_SetTrophy()` 的下游（`SlotByTrophy()` /
  `NF_Stage_PlaceDown()`）**一行未改** —— 补出来的名次与视觉写入的走同一条路。
  物料分支未动。
- **验证状态**：编译已验证（clean build，`-Wall` 零告警）；**实机未验证**。
- **备注**：
  1. **前提是 3 个奖杯都进了槽。** 少进一个时那个 `continue` 会连夹紧和转盘推进
     一起跳掉，采集时序本来就乱了 —— 所以**没有**单独判"这个槽到底进没进料"。
     反过来说，若某槽只是 IR 没触发但奖杯其实在（`wait_block_entered` 超时、
     该槽留 0），本函数照样能把它补出来，这正是想要的。
  2. 补出来的名次**没有任何视觉校验**，纯逻辑推导。所以查重复一旦触发就宁可
     不补 —— 那种情况下已知数据本身就已经不可信。
  3. 未做的优化：用户提到"前两个都识别成功则第三个可直接判断" —— 严格说还可以
     在第三个槽 `wait_block_entered()` 时传 `rank_out = NULL` **跳过投票**
     （省一段等待、也不会被错票污染）。本次没做，因为物块**仍然必须等它进料**，
     省下的只是投票那点开销；且跳过后 `NX_GetTrophyRank()` 不消费帧，
     残留帧会落到下一轮的开窗丢帧逻辑里，交互需要再确认。先保持"照常投票 +
     事后补全"，逻辑最直白。

#### V1.26.5 - 2026-10-06
- **修改类型**：修复（**找块游标只在上电时复位一次**）
- **涉及模块**：
  - 应用层 / `app/worker_task.c`（`NF_Stage_Collect()`）
- **修改内容**：

  `TT_RotateReset()` 原先只在 `NF_FlowSeed()` 里调，而 `NF_FlowSeed()` 被
  `s_flow_seeded` 门闩成**每次上电只跑一次**。于是**第二次按键开跑**（不重新上电）时
  `ColorIdentif.c` 的文件级游标 `s_seek_slot` 还停在上轮的位置：

  - 上轮走完（游标 = 5）→ `TT_SeekBlock()` 恒返回 0 → **整轮 FindCircle 全部
    "找不到或已放完"，一件都放不出去**；
  - 上轮只走了一半 → 游标从中间接着走 → **圆锥那一格被跳过**（`T1[0]` 直接顶上来）。

  修法：在 `NF_Stage_Collect(COLLECT_BLOCK)`（物料采集阶段，正好在
  `{Event_FindCircle, 5u}` 之前，且整轮只派发一次）补一句 `TT_RotateReset()`。
  `NF_FlowSeed()` 里那句保留不动。

- **影响范围**：物料放置路径的游标复位时机。`NF_FlowSeed()` 未改；物料/奖杯采集本身未改。
- **验证状态**：编译已验证（clean build，`-Wall` 零告警）；**实机未验证**。
- **备注**：**这是从 17:34 那批日志反推出来的，日志本身就是证据** ——
  `T1[0] = (BLUE, RECT)`，而 `TT_SeekBlock()` 第 0 次应返回**圆锥槽 1**；
  但那一轮第一次 FindCircle 打的是 `转盘物理槽 4`（= `T1[0]` 匹配到的槽），
  说明游标进来时已经是 1 而不是 0，即本上电周期里已经跑过一轮。

  ⚠ 同一批日志还暴露了另外四处**本次未改**的问题，见下方 2026-10-06 后续记录 / 现场分析：
  1. **形状阈值表与实测完全不重叠**（主因）—— `Slot_Shape[] = {460,462,472,468}`，
     实测 `raw` = 590/653/648/660，**全部 ≥ 阈值** → 四个槽一律判成 `SHAPE_RECT`，
     而 `T1[]` 要 2 个 `SHAPE_CYLINDER` → 那两项**永远匹配不上**。
     `raw=590`（槽 2）与 648/648/660 明显分簇，按 `Slot_Shape[]` 自己的注释
     （"两种物块各夹 20 次取两类不重叠区间的中点"）重标即可。
  2. **匹配失败不推进游标** → 后面每一拍都重试同一项，日志里连着 3 次同样的
     "找不到"。好处是不会错误推进，坏处是**一项匹配不上就把后面所有项全堵死**。
  3. **前两个槽的颜色是兜底值** —— `slot 2/3: color timeout -> default`，
     `collect_default_color()` 按 `slot <= 3 → RED` 猜的，不是测出来的。
     本次恰好凑成 2 红 2 蓝，与 `T1[]` 的颜色要求对得上，属于运气。
  4. `[PLACE] 前移没等齐到位 (超时)` / `后退没等齐到位 (超时)` ——
     `Mecanum_MoveBodyPos()` 轮询 `Emm_V5_Is_Reached()` 没等到到位。与本次改动无关。

#### V1.26.6 - 2026-10-06
- **修改类型**：新增（**形状的默认兜底表**，与颜色那张对称）
- **涉及模块**：
  - 业务层 / `app/block_collect.c`（新增 `collect_default_shape()`；`identify_slot()`
    在 `shape == SHAPE_UNKNOWN` 时兜底）
- **修改内容**：

  颜色早就有兜底（`MSP_Color_Wait()` 超时 → `collect_default_color(slot)`），形状没有。
  补上对称的一张：

  ```c
  static BlockShape_t collect_default_shape(uint8_t slot)
  {
      return (slot == 2u || slot == 4u) ? SHAPE_RECT : SHAPE_CYLINDER;
  }
  ```

  取值与 `collect_default_color()`（`slot <= 3 → 红`，否则蓝）**配对**，
  保证 4 个 `(颜色, 形状)` 恰好铺满 `T1[]`：

  | 物理槽 | 颜色(兜底) | 形状(兜底) | 对应 `T1` 项 |
  |---|---|---|---|
  | 2 | 红 | 方 | `T1[2]` (RED, RECT) |
  | 3 | 红 | 圆 | `T1[3]` (RED, CYLINDER) |
  | 4 | 蓝 | 方 | `T1[0]` (BLUE, RECT) |
  | 5 | 蓝 | 圆 | `T1[1]` (BLUE, CYLINDER) |

- **影响范围**：`identify_slot()` 的形状取值，仅在读失败时生效。物料/奖杯分支其余未改。
- **验证状态**：编译已验证（clean build，`-Wall` 零告警）；**实机未验证**。
- **备注**：
  1. ⚠ **这个兜底当前不会触发。** `BlockBasic_ShapeFromRaw()` 只在 `raw < 0`
     （舵机总线失败）或槽号越界时返回 `SHAPE_UNKNOWN`；而 17:34 那批日志里
     `raw` 是 590~660，**读成功了**，只是被过期的 `Slot_Shape[]`（460~472）
     判成了 `SHAPE_RECT` —— 属于"有效但错"的值，`== SHAPE_UNKNOWN` 恒假。
     所以**要真正生效，仍须重标 `Slot_Shape[]`，或改成无条件用默认表**。
  2. 哪个槽配方/圆**不影响能否找到** —— `TT_SeekBlock()` 是按 `(颜色, 形状)`
     的**值**搜槽的，四个组合齐全即可；它只决定方/圆分别摆到哪个点位
     （即 `T1[]` 里的先后）。所以配对在色内可互换，跨色不可。
  3. ★ 占位值 —— 与 `NF_SLOT_COLORS`/`NF_SLOT_SHAP` 一样是 NX 接入前的硬编码。
