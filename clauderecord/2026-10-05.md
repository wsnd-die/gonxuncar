#### V1.24.0 - 2026-10-05
- **修改类型**：新增（**航向误差死区**，压停车/直行时的小幅来回抖）
- **涉及模块**：
  - 业务层 / `app/NavigationMecanum.h`、`app/NavigationMecanum.c`
- **修改内容**：

  `Nav_GoToWorld()` 的航向通道是手写 PD（`w_w = NAV_KP_YAW·eyaw − NAV_KD_YAW·wz`），
  `NAV_KP_YAW = 5.0` 会把 OPS9 的航向噪声放大成"来回的角速度指令" —— 表现就是停车或
  直行时车头持续微摆。

  新增 `NAV_YAW_DEADBAND = 0.0175f`（≈1.0°，取容差的 1/3），**只喂控制器**：

  ```c
  float eyaw_dz = (fabsf(eyaw) < NAV_YAW_DEADBAND) ? 0.0f : eyaw;
  float w_w = NAV_KP_YAW * eyaw_dz - NAV_KD_YAW * PID_Filter(0.25, wz);
  ```

- **影响范围**：`Nav_GoToWorld()` 的航向输出；到达判据**不改**（仍用原始 `eyaw`）。
- **验证状态**：编译已验证（`-Wall` 零告警）；**实机未验证**。
- **备注**：
  1. **必须明显小于 `NAV_TOL_YAW`**：死区 ≥ 容差时误差会停在死区里不再被修正，而到达判据
     仍要求入容差 → 永远判不到"到达"，每段跑满 10s；且 `Nav_FeDuanPoint()` 超时**不推进游标**，
     会卡在同一个点上反复重试。
  2. 角速度那一路 (`pose.wz`) 当时复用了同一个宏（≈1°/s，偏小），后续按轴拆参数时再分。

#### V1.24.1 - 2026-10-05
- **修改类型**：新增（**平移轴速度规划**第一版）+ 修复（**软启动斜坡从未生效**、**Y 轴被写死为 0**）
- **涉及模块**：
  - 业务层 / `app/NavigationMecanum.h`、`app/NavigationMecanum.c`
- **修改内容**：

  ① 新增 `NAV_AxisRef()`：`v_ref = ±√(2·a_brk·|e|)`，配 8mm 位移死区 + `NAV_VMAX_XY`
  上限 + 加速度斜坡；意图是"远场跑满、近场按 √ 曲线收速，刚好停在目标点"。
  新增编译期开关 `NAV_XY_PROFILE`（=0 退回旧的位置 PD，用于 A/B）。

  ② 新增到位速度门限 `NAV_ARRIVE_VMAX`：到达判据从"三轴误差入容差"扩展为
  "**且指令速度已收下来**"。理由：位置进容差 ≠ 停住 —— 判到后立刻 `NAV_Stop()`
  是**一步跳到 0 速**（EMM_V5 的 `acc=0`），从 0.49 m/s 刹停要滑 ~4.8cm，比 2cm 容差还大。

  ③ **修复软启动斜坡白算**：原实现算了 `vx_cmd = NAV_Ramp(vx_cmd, vx_w, ...)` 之后，
  转世界→车体用的却是**未限幅的** `vx_w/vy_w` —— 斜坡结果被丢弃，起步一直是 PID 原输出。

  ④ **恢复 Y 轴**：原调用是 `Mecanum_Calc_Full_V(bvx, 0, w_w)`（第二个参数写死 0，
  `bvy` 算了就丢），Y 方向根本不执行 → 改为 `(bvx, bvy, w_w)`。

- **影响范围**：`Nav_GoToWorld()` 的平移通道全部；A/B 开关 `NAV_XY_PROFILE`。
- **验证状态**：编译已验证（两个宏分支都编过）；**实机结果不合格**，见 V1.24.2。
- **备注**：这一版上机后"**跑到点位来回晃，比原来的纯 P 还差**" —— 根因见 V1.24.2。

#### V1.24.2 - 2026-10-05
- **修改类型**：修复（**上一版的 √ 曲线不能当"参考"，只能当"上限"**）
- **涉及模块**：
  - 业务层 / `app/NavigationMecanum.h`、`app/NavigationMecanum.c`
- **修改内容**：

  参考速度改成 **近场线性 P + 远场制动曲线上限**：

  ```c
  static float NAV_AxisRef(float err, float v_max, float a_brk, float kp)
  {
      float v  = kp * err;                          /* 近场参考: 线性, 过零连续 */
      float vc = sqrtf(2.0f * a_brk * fabsf(err));  /* 远场上限: 此刻还刹得住 */
      if (v >  vc) v =  vc;
      if (v < -vc) v = -vc;
      return NAV_Clamp(v, -v_max, v_max);
  }
  ```

  同时**删掉位移死区**（线性项在 e=0 处连续到 0，没有边界可抖），新增按轴近场增益
  `NAV_KP_X_LIN` / `NAV_KP_Y_LIN`、远场 `NAV_BRK_X/Y`。

- **影响范围**：`Nav_GoToWorld()` 平移通道；`NAV_XY_PROFILE=0` 分支不受影响。
- **验证状态**：编译已验证；**实机未验证**（待跑 A/B：比较每点的 `t` 与 `ovs`）。
- **备注**：
  1. **根因**：√ 曲线当参考时有两个致命毛病 —— ① 等效增益在 e→0 时发散（d√e/de→∞）；
     ② 死区边界是 "0 → √(2·a·deadband)" 的**阶跃**。OPS9 位置噪声一到，指令就在
     0 和 0.2 m/s 之间以控制频率来回跳 → 正是"到点来回晃"。
  2. **曲线只在 `e > Vmax²/(2a)` 时才起作用**：按 `Vmax=2.0`、`a=2.5` 算是 0.8m ——
     点间距小于这个数时曲线完全不参与，纯粹是 `v = Kp·e`。
  3. `NAV_BRK_*` **必须 ≤ 斜坡能给的减速度**（`NAV_ACC_XY`），否则曲线在承诺一个
     斜坡给不出的减速 → 必冲过头；实测用日志里的 `ovs`（过冲量）二分它。
  4. 顺带修掉 `NAV_AxisRef` 里按 `'x'/'y'` 写的两段**逐字相同**且**都没有兜底 return**
     的分支（`-Wreturn-type`，返回值是垃圾）。

#### V1.24.3 - 2026-10-05
- **修改类型**：修改（**回家只走最后一点** + `NF_Start()` 兜底）+ 新增（调参仪表）
- **涉及模块**：
  - 应用层 / `app/worker_task.c`、`app/worker_task.h`
  - 业务层 / `app/NavigationMecanum.c`
- **修改内容**：

  ① **回家不再走全表**。`NF_Stage_GoHome()` 原调 `Nav_RunWaypoints()` —— 那是**从 0 号点
  把整张表再走一遍**（17 点），而流程自己前面已经用十几段导航走过一遍 → 现场表现是
  **"连着跑两遍"**。改为只走到表的最后一行（"17 回家点"）：

  ```c
  if (g_waypoint_count > 0u) {
      const World_Dir_t *home = &g_waypoints[g_waypoint_count - 1u];
      (void)Nav_GoToWorld(home->x, home->y, home->yaw);
  }
  ```

  ② **`NF_Start()` 判返回值**。原实现 `NF_DispatchNext(&mode)` 不判返回 —— 表跑完时它
  返回 `false` 且**不写 out**，于是把未初始化的栈值当阶段号发出去（随机跳一个阶段）。
  改为判返回值 + 打一行"表已跑完, 忽略启动键"。

  ③ **加调参仪表**：`Nav_GoToWorld()` 出循环时打一行，含耗时、末态 `ex/ey/eyaw`、
  末速度、**过冲量 `ovs`**（取第一拍误差符号 `s0`，之后每拍算 `-s0·e` 取最大 ——
  误差不反号时恒为 0，冲过目标点就是冲出去多远）；超时那一路补打末态误差
  （它声明在循环内层，原来看不到，需每拍存一份）。

- **影响范围**：流程的收尾路径；`Nav_GoToWorld()` 的日志（不影响控制）。
- **验证状态**：编译已验证；**实机已验证**（日志确认回家只多走 1 个点，不再是 17 个）。
- **备注**：`ovs` 是调 `NAV_BRK_*` / `NAV_KP_*_LIN` 的**唯一客观依据**（比肉眼看车准）。

#### V1.24.4 - 2026-10-05
- **修改类型**：新增（**采集点位"到位后向前蹭料"**）
- **涉及模块**：
  - 应用层 / `app/worker_task.c`（参数 + `NF_CreepForward()` + 挂载点）
  - 业务层 / `app/NavigationMecanum.h`、`.c`（新增 `Nav_LastWaypointNo()`）
- **修改内容**：

  现场问题：物料/奖杯点位上，位置环判"到位"时车头离物块还差一点 → 进料口 IR 不触发
  → 采集侧 `wait_block_entered()` 干等超时，物块收不到。

  在 `NF_Stage_Navigation()` 的 `NF_RouteStep()` 之后、派发下一阶段**之前**加一步
  "向前蹭一小段"：

  ```c
  #define NF_CREEP_FWD_M       0.06f    /* 前进距离上限 (m) —— 限幅一 */
  #define NF_CREEP_VMPS        0.06f    /* 蹭的速度 (m/s); 顶不动就提到 0.10 */
  #define NF_CREEP_TIMEOUT_MS  1200u    /* 总时长上限 (ms) —— 限幅二 */
  static const uint8_t NF_CREEP_WP[] = { 1u, 2u, 3u, 7u, 8u, 9u, 10u, 11u };

  if (arrived && !Nav_LastAborted() && NF_NeedCreep(Nav_LastWaypointNo())) {
      NF_CreepForward();
  }
  ```

  `NF_CreepForward()` 的要点：
  - **车体系**速度指令 `Mecanum_Calc_Full_V(v,0,0)` —— 不依赖 OPS9（就是它把车停在了物块前面）；
  - 停的条件 = 物块**完全进入**进料口：判据与 `collect_ir.c` 的 `IR_ObjectEntered()` 一致
    （上一拍遮光 → 这一拍恢复 + 复确认一拍防毛刺），但**用本函数自己的边沿状态** ——
    `IR_ObjectEntered()` 内部那个 static 归 `gripper_task` 的 `wait_block_entered()` 专用，
    两边抢同一份状态会互相破坏。所以只调纯电平的 `IR_ObjectPresent()`；
  - 距离 + 时长**双限幅**，蹭不进去也不会一直顶；
  - 结束时 `AG_Stop()`，并**消费掉** `g_route_abort`（见 V1.24.5）。

- **影响范围**：所有 `NF_CREEP_WP[]` 列出的点位；`Nav_FeDuanPoint()` 新增一个对外 getter。
- **验证状态**：编译已验证；**实机已验证**（`[FLOW] creep: travel=50mm`）。
- **备注**：
  1. 实测**每次都跑满限幅**（travel ≈ 50mm）→ IR 的"完全进入"在该机构上晚于 1.2s 才成立，
     实际是**距离上限**在收尾；功能没问题（物块确实被顶进去了），要它靠 IR 停得看 IR 的
     安装位置/物块几何。
  2. `NF_CREEP_WP[]` **必须覆盖所有会进料的点位** —— V1.24.5 之后采集完全依赖 creep 顶料，
     漏一个那个槽就会干等超时。
  3. ⚠ 蹭料**移动了车但不刷新 `Self_Dir`**（OP9 位姿）：之后凡是用 `Self_Dir` 的**相对移动**
     （`Nav_MoveBody()`、`Place()` 里那些）都会带上这 6cm 偏差。**待修**。

#### V1.24.5 - 2026-10-05
- **修改类型**：修复（**收完第 1 个奖杯后跳掉第 2 个点位**）
- **涉及模块**：
  - 应用层 / `app/worker_task.c`、`app/worker_task.h`
  - 业务层 / `app/NavigationMecanum.h`、`.c`（`g_nav_running`）
- **修改内容**：

  **现象**：采集完第 1 个奖杯后，第 2 个点位的导航"凭空消失"（车没动），游标却推进了，
  直接去下一个点采集。

  **根因链**（V1.24.4 的 creep 引入的新窗口）：
  1. creep 保证了"车**到位之后**物块才被顶进进料口" —— 于是"物块进料"这个事件发生在
     **导航段结束之后**；
  2. 而进料事件是从 `gripper_task` 上报的，它的 `IR_ObjectEntered()` 内部有 `osDelay(50)`
     + `osDelay(100)` 去抖 → 比导航侧的检测**晚 50~150ms**；
  3. 那个"打断当前路线段"的请求落到的是**下一段刚起步**的窗口里 → 下一段第一拍就命中，
     `Nav_GoToWorld()` 立刻返回（`Nav_LastAborted()` 为真），而 `Nav_FeDuanPoint()` 照常
     `s_idx++` → **平白吃掉一个点位**。

  **两次不成功的尝试**（都记下来，避免以后重走）：
  - ① 在 `NF_RouteStep()` 开头清 `g_route_abort` —— **不够**：清完之后 `Nav_GoToWorld()`
    还有 `osDelay(20)` 让路窗口，且打断本身可能迟到 150ms，任何"在某个时刻清标志"的
    写法都堵不住；
  - ② 加 `g_nav_running`（`Nav_GoToWorld()` 进驱动循环前置 1、三个出口清 0），
    `Route_AbortRequest()` 只在有段在跑时才置标志 —— 也不够：迟到的那次，段**确实在跑**。

  **最终修法**：`NF_ABORT_ON_FEED`（默认 **0**）—— **进料事件不再打断路线段**。
  理由：在"分点导航 + 到位蹭料"模式下，物块**只可能**在车到位之后进料，那时根本没有段
  可以打断；这个打断机制原本是给"边开边收"（车一边开一边把物块扫进进料口）设计的。

  ```c
  void Route_AbortRequest(void)
  {
  #if NF_ABORT_ON_FEED
      if (g_nav_running) { g_route_abort = 1u; }   /* 旧语义, 保留 */
  #endif
      /* 默认: 直接丢弃 */
  }
  ```

- **影响范围**：
  1. 游标**只由"到达"推进** → 一步一点、完全确定（走不到就**卡点**，日志是
     `[NAV] 分点导航第 N 点超时, 游标停在原点待重试`；这正好是区分"卡点/跳点"的标志）；
  2. `[NAV] 第 N 点被 IR 打断, 游标 -> N+1` 这行**不再出现**（机制关了，不是坏了）；
  3. `Nav_FeDuanPoint()` 的打断分支、`Nav_LastAborted()` 恒为 false → 成为死代码/恒假；
  4. **采集侧从此完全依赖 creep 顶料**（没有"边开边收"兜底）。
- **验证状态**：编译已验证（`NF_ABORT_ON_FEED` 两个分支都编过）；**实机已验证**
  （日志确认游标 1→2→3→4→5 连续、点 2 有 ARRIVE 记录）。
- **备注**：
  1. ⚠ **圆弧模式**：`Arc_Run()` 也认 `g_route_abort`，但它不会置 `g_nav_running` ——
     打开 `NF_ROUTE_ARC=1` 之前，要在 `Arc_Run()` 的驱动循环前后补同样的置位/清零，
     否则跑圆弧时进料打断会失效。
  2. 宏改回 `1` 即恢复旧语义（`g_nav_running` 那套保留着）。

#### V1.25.0 - 2026-10-05
- **修改类型**：新增（**丝杆绝对位置指令**）+ 修改（5 处调用点迁移）+ 修复（文档方向写反）
- **涉及模块**：
  - 硬件驱动层 / `hardware/actuators/block_basic.h`、`.c`
  - 应用层 / `app/worker_task.c`、`app/block_collect.c`
  - CubeMX 生成 / `Core/Src/app_freertos.c`（`gripper_task` 初始化）
- **修改内容**：

  原 `BlockBasic_LiftTo(uint8_t dir, float pos)` 是**相对**指令，`dir` 决定方向、
  `pos` 是相对量，内部用文件级 static 累计 `lift_current`。这套写法有硬伤：
  **顺序相关** —— 中间某一拍被跳过（例如 PlaceDown 走"名次找不到, 跳过"分支），
  后面所有高度就整体错位；而且超量程时**静默返回 0 且不动作**，调用方无从分辨。

  新增绝对版（旧的保留，`lift_current` 提到文件作用域、两版共用）：

#### V1.25.5 - 2026-10-05
- **修改类型**：修复（**NX 坐标帧被 `0xFF` 提前截断**）
- **涉及模块**：
  - 硬件驱动层 / `uart/NX_uart.c`（`NX_RxProcessByte()` 的 `NX_RX_COLLECT`）
- **修改内容**：

  **现象**：NX 侧发的圆心 xy 在 STM32 侧收不到，`Circle_base.c:52` 那句
  `printf("%f\r\n", dist)` 恒打 `0.000000`。

  **根因（本文件这一半）**：B5 帧是 `A3 B5 cxH cxL cyH cyL FF`，而收包判据是
  "**撞到 `0xFF` 就当包结束**"。但 `0xFF` 在这个帧里是**合法载荷** —— 负数的二补码
  高字节恒为 `0xFF`（`cx ∈ [-256,-1]` → `cxH = 0xFF`）。

  而"圆心居中"的判据是 `dx² + dy² < area_of_center(=10)`，即 `|dx|,|dy| ≤ 3`，
  **正好整段落在"高字节 = 0xFF"的区间里**（`-3/-2/-1` 三个值）。
  于是包在 `rx_idx = 3` 就"结束"，`rx_idx >= 7` 不成立 → 落到 `else` → `rx_err++`，
  坐标整帧丢弃。按 `dx,dy` 在 `{-3..3}` 上粗估，**'O' 帧里只有约 `(4/7)² ≈ 33%`
  能活下来** —— 三分之二的坐标帧就这么没了。

  修法（用户选定"STM32 改按长度收包"）：**B4/B5 改成定长收包，不再看 `0xFF`**；
  B3 是变长（5B/7B）且载荷是字母、不会撞 `0xFF`，保留 `0xFF` 终止符。

  ```c
  if ((NX_ctx.rx_pkt_type == 0xB4 && NX_ctx.rx_idx >= 4u) ||
      (NX_ctx.rx_pkt_type == 0xB5 && NX_ctx.rx_idx >= 7u) ||
      (NX_ctx.rx_pkt_type == 0xB3 && b == 0xFF)) {
  ```

- **影响范围**：NX 方向帧 / 坐标帧的解析；**发送端格式未动**（Python 与 K230 版都不用改）。
  `rx_buf[8]` 容得下 B5 的 7 字节，溢出判据 `rx_idx >= 8` 保持不变。
- **验证状态**：编译已验证（clean build，`-Wall` 零告警）；**实机未验证**。
- **备注**：
  1. ⚠ **这只是两个根因里的一个。** 另一个在发送端：`circle_pc_v1.py` 的
     `_send_circle_xy()` **只在 `dat_pos == 'O'` 分支里被调用**，N/S/E/W 只发方向帧、
     不带坐标 —— 所以非 'O' 期间总线上根本没有 0xB5 帧。**用户知悉，自行修改**
     （改成每帧都发）。两处都修完，`dist` 才会在所有方向下都有值。
  2. **"分档调速是死的"与此无关**：`Circle_base.c:48-51` 用坐标分档，但非 'O' 期间
