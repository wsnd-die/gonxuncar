#### V1.19.4 - 2026-09-29
- **修改类型**：新增（**兼容升级** —— 纯新增函数，不改动任何既有接口或行为）
- **涉及模块**：
  - 硬件驱动层 / `hardware/actuators/servo_scs.h`（新增声明）
  - 硬件驱动层 / `hardware/actuators/servo_scs.c`（新增定义）
- **修改内容**：

  按用户要求（2026-09-29）新增 **`Scs0009_ReadRaw(uint8_t id)`** —— 读 SCS0009
  （本工程 ID 2~6）当前位置的便捷封装。

  ```c
  int Scs0009_ReadRaw(uint8_t id)
  {
      if (SCS_FeedBack(id) < 0) {
          return -1;                  /* 超时/校验失败, 原因看 SCS_GetLastError() */
      }
      return SCS_ReadPos(-1);         /* 从缓冲区取, 不再占总线 */
  }
  ```

  返回原始位置 **0~1024**（10 位编码器 ↔ 0~300°，中位 500；角度换算
  `deg = raw / 1024.0f * 300.0f`），失败返回 -1。

  **为什么走缓冲区路径而不是 `SCS_ReadPos(id)` 直连** —— 这是本次唯一的
  技术要点，字节序问题：

  | 路径 | 字节序来源 | 后果 |
  |---|---|---|
  | 直连 `SCS_ReadPos(id)` | `readWord` → `SCS2Host`，按**全局 `End`** 解释 | SCS/CL 系列要大端，调用方须先 `SCS_SetEnd(1)` |
  | 缓冲 `SCS_ReadPos(-1)` | 厂商库**硬编码大端**（`scslib/SCSCL.c:110-113`），**不看 `End`** | 正好是 SCS 系列要的 → 与 `End` 当前值无关 |

  直连那条路的隐患是真实的：`SCS_SetEnd()` 与 `SCS_ReadPos()` 是**两次独立
  取锁**，中间被别的系列的写命令翻掉 `End`（本工程 UART5 上 ID1 转盘的
  `SCS_WritePosEx()` 会 `scs_little_endian()`、ID2~6 的 `SCS_WritePos()` 会
  `scs_big_endian()`），就会读到**字节交换的错值且不报错**。
  走缓冲区路径则从根上不依赖 `End`。

- **备注**：

  1. **【使用限制】阻塞在总线往返上，不要在控制环里调。**
     单次最长 `SCS_UART_RX_TIMEOUT_MS` = 100ms（舵机不在线时）。
     适用场景是低频命令任务，如 `gripper_task`。
  2. **【必须知悉】`Mem` 是厂商库的共享静态缓冲，本函数不是原子操作。**
     `SCS_FeedBack()` 与随后的 `SCS_ReadPos(-1)` 是**两次独立取锁**，中间若被
     另一个任务插一次 `SCS_FeedBack(别的 id)`，读回来的会是**别的舵机的值**
     （值域相近，不一定看得出来）。目前全工程只有本函数走这条路径，安全；
     **以后再加第二个读取点时必须处理**。

     > 不能靠"在调用方用 `SCS_Lock()` 把两步包起来"解决：本文件的总线互斥锁
     > **不是递归锁**（`s_mutex_attr` 只有 `osMutexPrioInherit`），而
     > `SCS_FeedBack()` / `SCS_ReadPos()` 内部各自会取锁 —— 嵌套取锁会在
     > `SCS_MUTEX_TIMEOUT_MS`(200ms) 后超时并**降级为无锁执行**
     > （`servo_scs.c` 的 `SCS_Lock()`），既白等又失去保护。
     > 真要做成原子，得像写函数那样在**同一个包装函数内部**
     > `SCS_Lock()` → 操作 → `SCS_Unlock()`，而不是在调用方加锁。
  3. **【命名】** 本文件既有函数一律 `SCS_` 前缀（如 `SCS_ReadPos`），
     `Scs0009_ReadRaw` 的 `Scs0009_` 前缀与之不一致。按用户指定保留原名；
     若要统一风格可改为 `SCS_ReadPosScs0009`，但需同步改 .c/.h 两处。
  4. **【相关坑，本次未动】** `SCS_ReadPos(id)` 直连路径需要调用方自行声明
     字节序这件事本身仍是无保护的（同 V1.19.x 系列里多次记录的"接口契约靠
     注释约定"）。若将来读 STS3032（ID1）的位置，注意**不能**用 `-1` 缓冲区
     路径 —— 那条路写死大端，对 STS 系列是字节交换的错值
     （`servo_scs.h` 已有说明）。

#### V1.19.5 - 2026-09-29
- **修改类型**：修复（**修复回读跑一会儿就恒为 -1**）
- **涉及模块**：
  - 硬件驱动层 / `hardware/actuators/servo_scs.c`（`ftBus_Delay()`、`Scs0009_ReadRaw()`）
  - 硬件驱动层 / `hardware/actuators/servo_scs.h`（`Scs0009_ReadRaw()` 的文档）
- **修改内容**：

  用户 2026-09-29 反馈：`Scs0009_ReadRaw()` 刚跑正常，**跑一会儿就变成 -1**。
  定位到根因是**厂商的 `rFlushSCS()` 是个假刷新**，据此做了两处修改。

  1. **`ftBus_Delay()` 增加「排空 RX + 清错误标志」。**

     ```c
     // scslib/SCSerail.c:45 —— 注释写着「接收缓冲区刷新」，实现只有延时
     void rFlushSCS() { ftBus_Delay(); }
     ```

     `rFlushSCS()` 是 `Read()` / `Write()` 每条命令前都会调的"刷新"，而它
     **根本不清 RX**。于是残留字节留在 UART 里，下一次命令的 `checkHead()`
     （`scslib/SCS.c:424`）会在**残留帧的 `FF FF` 上立刻对齐**：

     - 读到的从机 ID 是**上一帧那颗舵机**的 → `bBuf[0] != ID` →
       `SCS_ERR_SLAVE_ID` → `Read()` 返回 0 → 回读函数返回 **-1**；
     - `checkHead()` 最多只吃掉 11 字节，而 `SCS_FeedBack()` 的回帧有 21 字节
       （`Mem` = `PRESENT_CURRENT_H(70) - PRESENT_POSITION_L(56) + 1` = 15 字节
       数据 → 2+1+1+15+1+1 = 21），**吃不干净 → 残留继续留给下一次
       → 永久级联错位**。这正是"跑一会儿就恒为 -1"。

     残留的两个来源（两条都会真实发生）：
     1. **ORE 溢出**：G4 的 UART **没有 RX FIFO**，1M 波特率下逐字节轮询两次读
        RDR 之间超过约 10µs 就丢字节；而本 HAL 版本的阻塞接收
        **完全不检查 ORE/FE/NE**（`stm32g4xx_hal_uart.c` 的 `HAL_UART_Receive`
        内层循环只等 `RXNE`），溢出是**静默**的，帧被"错位填充"，校验和必不符；
     2. **收帧途中被抢占**：`gripper` 是 `osPriorityNormal`(24)，而
        `ops9imu_task` / `NLF_TASK` 是 `osPriorityHigh`(40)。

     修改（放在本工程的胶水文件里，**不动厂商库**）：

     ```c
     void ftBus_Delay(void)
     {
         /* 1. 排空 RX 残留（读 RDR 同时清 ORE） */
         while (__HAL_UART_GET_FLAG(&SCS_UART, UART_FLAG_RXNE) != RESET) {
             (void)SCS_UART.Instance->RDR;
         }
         /* 2. 显式清 ORE/FE/NE —— RXNE 已空但 ORE 仍挂着的场合靠这一步 */
         __HAL_UART_CLEAR_OREFLAG(&SCS_UART);
         __HAL_UART_CLEAR_FLAG(&SCS_UART, UART_CLEAR_FEF);
         __HAL_UART_CLEAR_FLAG(&SCS_UART, UART_CLEAR_NEF);

         if (osKernelGetState() == osKernelRunning) { osDelay(SCS_BUS_DELAY_MS); }
         else                                       { HAL_Delay(SCS_BUS_DELAY_MS); }
     }
     ```

     效果：一次丢同步**只是失败一次**，下一条命令从干净状态开始，
     不再级联成永久错误。

  2. **`Scs0009_ReadRaw()` 由「15 字节批量读」改为「锁内设大端 + 直读 2 字节」。**

     原实现走 `SCS_FeedBack()` + `SCS_ReadPos(-1)`（当初选它是为了绕开字节序
     竞态，因为缓冲区路径在厂商库里硬编码大端）。但它要读寄存器 56~70 共
     **15 字节**，回帧 **21 字节**（@1Mbps ≈ 210µs）—— 收帧越久越容易被抢占
     打断而丢同步，正是上面那个 bug 的触发条件。

     改为：

     ```c
     int Scs0009_ReadRaw(uint8_t id)
     {
         int held = SCS_Lock();
         scs_big_endian();               /* 锁内设, 不会被插队翻掉 */
         int r = ReadPos(id);            /* 只读寄存器 56, 2 字节 */
         if (held) { SCS_Unlock(); }
         return r;
     }
     ```

     回帧降到 **8 字节**（≈ 80µs），脆弱窗口缩短 **2.6 倍**；同时字节序仍是
     安全的 —— 在**同一个包装函数内部**设 `End`，别的任务无法插队
     （对比：在调用方 `SCS_SetEnd()` + `SCS_ReadPos()` 是两次独立取锁，
     中间会被转盘 ID1 的 `SCS_WritePosEx()`（切小端）翻掉）。

     这个改法同时淘汰了 V1.19.4 的缓冲区路径，也就**顺带消除了 `Mem`
     共享静态缓冲带来的"两次取锁之间被插队"问题**（V1.19.4 备注 2）。

- **影响范围**：

  - **`ftBus_Delay()` 在每条 SCS 命令前都会被 `rFlushSCS()` 调用**，
    所以本修复对**全部** SCS 收发（写位置、同步写、EPROM 操作、回读）都生效。
    排空是纯读寄存器操作（不阻塞、不等总线），耗时在纳秒级，不影响时序。
  - `Scs0009_ReadRaw()` 的签名未变，调用方（`app_freertos.c` 的
    `gripper_task`）无需改动。
  - 未改动厂商库 `scslib/` 任何文件。
  - **未改动 `SCS_ReadPos()` / `SCS_FeedBack()` 本身**，它们的行为与原来一致
    （仍要求调用方自行声明字节序）。若将来读 STS3032（ID1）的位置，
    注意**不能**用 `SCS_ReadPos(-1)` 缓冲区路径 —— 那条路写死大端，
    对 STS 系列是字节交换的错值。
  - 编译无新告警。

- **备注**：

  1. **【本轮是"打断级联"，不是"消灭错帧"】** 修改后丢同步的概率没有降低到零
     —— 30 号那条根治要靠硬件（给 RX 加 FIFO/DMA 收帧）或让收帧不被抢占。
     收益是**把永久性故障降级为偶发故障**，对上层可恢复。
  2. **【若仍频繁 -1】** 下一步查 `SCS_GetLastError()` 的取值分布：
     恒为 `1`（无应答）指向接线/供电；`2`/`4` 指向持续丢字节，
     那时考虑把 `gripper` 优先级提到 `ops9imu` 之上，或改用 DMA 收帧。
  3. **【文档勘误】** `servo_scs.h` 文件头的栈要求警告里写「本工程 `gripper`
     任务当前只有 **512 字节**栈（`app_freertos.c:81`）」，实测当前是
     **1024 字节**（`gripper_attributes.stack_size = 256 * 4`，CMSIS-RTOS2 里
     `stack_size` 单位是字节）。数值已过时，但"1KB 余量"的要求仍成立
     （`SyncWritePosEx` 的 `offbuf[32*7]` = 224 字节 + printf）。
     **本次未改该注释**，仅记录。
