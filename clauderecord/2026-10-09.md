#### V1.29.0 - 2026-10-09
- **修改类型**：新增（**圆弧运行中"采集完成即收尾"—— 不再等弧跑满**）
- **涉及模块**：应用层 / `app/NavigationMecanum.c`（`Nav_Cricle()` 主循环的打断分支）
- **修改内容**：

  **背景**：`Event_Collect_L` → `NF_Stage_Collect(COLLECT_BLOCK)` 在挂起采集请求的
  同时挂了 `Event_NavCircleL`，于是 `Nav_Cricle()` 与 `gripper_task` 的采集状态机
  **并行**运行（V1.23.0 的解耦）。原意是"车一边跑弧一边把物块收进来"，但弧是
  **阻塞跑满 170°** 的 —— 采集先结束也不能让弧提前收尾，车会白跑完剩下的弧才进
  导航。本次给弧加上"采集完成 → 立刻收尾"的出口。

  **① 主循环新增完成判据（用公开接口，不自立标志）**

  ```c
  if (BlockCollect_IsDone())          /* app/block_collect.c 的公开查询接口 */
  {
      printf("[NAV-ARC] ABORT 采集完成 swept=%.3f rad\r\n", swept);
      break;
  }
  ```

  `break` 后走的是原有出口：`NAV_Stop()` → 刷新 `Self_Dir` → `g_nav_running = 0`
  → `NLF_Request(Event_Navigation)`，即**直接进导航阶段**（本文件末行，未改）。
  导航侧 `NF_Stage_Navigation()` 对 `cur_stage == COLLECT_BLOCK` 的 `need = 1u`，
  所以接着只走**一个** `g_waypoints[]` 点就 `NF_DispatchNext()` 到 `Event_FindCircle`。

  **② 删除一段恒假的残码**

  上一版此处写的是：

  ```c
  volatile bool s_done    = false;    /* ← 函数内【局部变量】, 全函数无人赋值 */
  ...
  if (s_done) { g_route_abort = 0u; printf("[NAV-ARC] ABORT ..."); break; }
  ```

  该 `s_done` 是 `Nav_Cricle()` 的局部量，初值 `false` 且**没有任何一处赋值**，
  判据**恒为假** —— 分支永不进入，且 GCC 不报错（变量被读，连
  `-Wunused-variable` 都不给），属**静默失效**。它与 `block_collect.c` 里同名的
  那个（`extern volatile bool s_done`，`BlockCollect_IsDone()` 的返回源，见该文件
  :33 / :378）**毫无关系**：不同作用域。已整段删除，改用公开接口。

- **影响范围**：仅 `Nav_Cricle()` 一个出口。`Nav_GoToWorld()` / `Nav_FeDuanPoint()`
  / `NF_RouteStep()` 等导航路径**一行未动**；`g_route_abort` 那条打断路径也**没动**
  （它当前是死码，见备注 2）。接口**兼容**：`Nav_Cricle()` 签名未变，
  未新增对外符号。
- **验证状态**：编译已验证（`cmake --build --preset Debug`，exit 0，
  `NavigationMecanum.c` **零告警**）。**实机未验证** —— 需现场确认"弧中途收完
  物块时车确实就地收尾、而不是跑满 170°"。
- **备注**：
  1. **进弧时 `BlockCollect_IsDone()` 必为 `false`，不会第一拍就误触发**：
     `NF_Stage_Collect()` 在挂弧请求前已 `BlockCollect_Reset()`（置
     `s_done = false`，`block_collect.c:374`）与 `BlockCollect_Start()`（同样置
     false，:366）；而本弧是在 `NF_Stage_Collect()` **返回后的下一拍**才真正开始
     跑的。这条链是本次改动正确性的前提，若将来调整 `NF_Stage_Collect()` 内
     那几行的顺序，需重新确认。
  2. **`g_route_abort` 那条打断路径仍是死码**（本次未启用）：置位点只有
     `Route_AbortRequest()`（`worker_task.c:53`），其函数体整个被
     `#if NF_ABORT_ON_FEED` 包着，而 `NF_ABORT_ON_FEED` 默认 `0`（`:50`）
     —— IR 进料调用它等于空操作。本次新增的完成判据**不依赖**这个开关。
  3. **潜在隐患（本次未改）**：`BlockCollect_Start()` 开头是
     `if (s_running) { return; }`，而此时 `s_done` 的清除在**这行之后** ——
     若上一轮采集仍在跑，这次的请求会被整个丢掉（`s_req` 不置位）。当前流程里
     两次采集之间隔着 Navigation / PlaceDown（秒级到十几秒），实际不会撞上；
     但若将来把采集阶段排得更密，需把 `s_done = false;` 提到 `if` 之前。
  4. **并行下的总线互斥**（V1.23.0 起的老问题）：弧运行期间 `NLF_TASK` 与
     `gripper_task` 共用 UART5 舵机总线而无互斥。目前弧内只在开头调一次
     `BlockBasic_LiftToAbs(0)`，中途不碰舵机，所以安全；但既然本次让弧提前退出、
     采集还在跑，**收尾的 `NAV_Stop()` 与采集的转盘/夹爪动作时间上更容易重疊**
     —— 现场若出现舵机偶发丢帧，优先查这里。
