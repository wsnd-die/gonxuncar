#### V1.26.7 - 2026-10-07
- **修改类型**：新增（**颜色采集改为窗口内投票**）
- **涉及模块**：
  - 硬件驱动层 / `hardware/sensors/msp_color.h`、`.c`（新增 `MSP_Color_Vote()` /
    `MSP_COLOR_VOTE_MS`）
  - 业务层 / `app/block_collect.c`（`identify_slot()` 改用投票取色）
- **修改内容**：

  **现象**：物块颜色"四个槽里随机挂两个" —— 17:34 那轮槽 2/3 超时，00:22 那轮槽 4/5 超时，
  超时的槽走 `collect_default_color()` 兜底（按"槽 ≤3 红、槽 >3 蓝"猜），颜色不可信。

  **根因（两条，都指向 `MSP_Color_Wait()`）**：

  ```c
  bool MSP_Color_Wait(Color_TypeDef *out, uint32_t timeout_ms)
  {
      s_msp.pending = 0u;                 /* ① 一进来就把手上那帧丢掉 */
      ...
      if ((HAL_GetTick() - t0) > timeout_ms) return false;   /* ② 窗口只有 300ms */
  }
  ```

  ① 的取舍本身没错（当时怕手上那帧是**上一槽**的），但**调用点早就不满足那个前提了**：
  `identify_slot(slot)` 是在 `TurntableTo(slot+1)` **之前**调的，也就是转盘**已经停在
  槽 N、物块也进来了**之后才调 —— 此刻 `pending` 里那帧就是**本槽**的，丢掉它等于白白
  再等一个周期。

  ② 于是一帧的判定完全赌在"下一个串口帧要在 300ms 内到"。芯片实际帧率未知，
  一低于 ~3 Hz 就**随机超时** —— 正是"每轮挂两个、位置还不固定"的样子。

  **修法（用户提议，与奖杯名次投票同一思路）**：新增 `MSP_Color_Vote(window_ms, out)`，
  在窗口内把 `MSP_Color_Take()` 收到的帧**全部计入票**，最后取多数：

  ```c
  for (;;) {
      while (MSP_Color_Take(&c)) { if (c < COLOR_COUNT) votes[c]++; }
      if ((HAL_GetTick() - t0) >= window_ms) break;
      osDelay(10);
  }
  ```

  - **不预先丢残留帧** —— 理由见上（这是与 `MSP_Color_Wait()` 相反的取舍）。
  - 平票取先遍历到的（RED 优先），用 `>` 不是 `>=`。
  - 窗口内一票都没有才返回 `false`，调用方走兜底表。
  - 窗口长度 `MSP_COLOR_VOTE_MS`，初值 **600ms**，★待现场实测调整。

  `identify_slot()` 里 `MSP_Color_Wait(&c, MSP_COLOR_TIMEOUT_MS)` →
  `MSP_Color_Vote(MSP_COLOR_VOTE_MS, &c)`。`MSP_Color_Wait()` 按第 5.3 节**保留不删**
  （当前无调用者）。

- **影响范围**：物料采集的取色；奖杯采集不受影响（`wait_block_entered()` 传 NULL 不投颜色票）。
  每槽采集时间上限增加 `MSP_COLOR_VOTE_MS`。
- **验证状态**：编译已验证（clean build，`-Wall` 零告警）；**实机未验证**。
- **备注**：
  1. **窗口长度的确定方法**：跑一轮，数日志里每个槽打了几行 `[MSP] color='x'` ——
     那就是窗口内的票数。**至少要有 3 票**才谈得上"多数"，不够就把
     `MSP_COLOR_VOTE_MS` 往上加。每加长一点会拖慢采集（每槽多等这么久）。
  2. ⚠ `MSP_Color_Take()` 内部有一行 `printf`，所以投票期间**每帧打一行**。
     这是现在唯一能看到帧率的窗口，先用着；确认帧率后可以摘掉降噪。
  3. 另一条**未修**的独立疑点：色字符不是 `'r'`/`'b'` 时 `pending` **根本不置位**
     （`msp_color.c` 的 `MSP_RX_COLOR` 分支只认这两个），那种物块会**必然超时**，
     与窗口长短无关。用 `MSP_Color_GetDiag()` 的 `rx_unknown` 计数可确认
     （非零 = 收到过不认识的色字符）。
  4. 形状那一维未动，仍是 `Slot_Shape[]` 阈值问题（见 2026-10-06 的 V1.26.6 备注）。

#### V1.26.8 - 2026-10-07
- **修改类型**：新增（**调试打印**）
- **涉及模块**：应用层 / `Core/Src/app_freertos.c`（`FC_TASK` 轮询循环）
- **修改内容**：在 `FC_TASK` 的 `MSP_Color_Take(&CCC);` 后面加一行
  `MSP_Color_DebugPoll();`，把每帧的**颜色字符与 RGB 原始串**打出来：

  ```
  [MSP-RX] color='r' rgb_raw="2003040"
  ```

  沿用 V1.20.7 已有的 `MSP_Color_DebugPoll()`，**驱动层一行未改**。`MSP_Color_Take()`
  自身那行 `[MSP]` 只给颜色，RGB 在它里面拿不到（数字段是 `msp_color.c` 的私有静态量），
  所以借 DebugPoll 的打印。
- **影响范围**：仅 `FC_TASK` 的调试输出；不影响采集逻辑（`MSP_Color_DebugPoll()` 只读
  `frame_ready`/`digits`，不消费 `pending`）。
- **验证状态**：已上机（2026-10-07 15:32）—— **`[MSP-RX]` 一行都没打印**。临时加回的
  `MSP_Color_GetDiag()` 打印给出决定性数据：

  ```
  [MSP-DIAG] bytes=0 chars=0 ok=0 unk=0     ← 每 1s 一次，恒为 0
  ```

  **USART2 的 RX 上一个字节都没有**，问题不在解析器、不在颜色判定。
- **备注**：
  1. **`bytes=0` 排除了波特率** —— 波特率配错照样会收到"乱码字节"，`rx_bytes` 会涨。
     只剩两种可能：
     - **RX 线上没有电平活动**：MSP 发送端没在发 / TX 没接到 **PA3** / 没共地；
     - **DMA 接收没挂上**：`MSP_StartRx()` 里 `HAL_UARTEx_ReceiveToIdle_DMA()` 失败时
       是 **静默 `return`**（`msp_color.c:44-46`），不会报错。判据：
       `huart2.RxState == 0x22`(BUSY_RX) 且 `hdma_usart2_rx.Instance->CCR & DMA_CCR_EN`。
  2. ⚠ **接线要点**：本工程 USART2 的 **TX 是 PD5、RX 是 PA3**（`usart.c:424-425`），
     不是常配的 PA2/PA3 一对。MSP 的 TX 必须落在 **PA3**。
     另注意 **printf 也走 USART2（PD5）**，即调试串口与 MSP 是**同一路 USART2**：
     电脑串口助手的 TX 不要再并到 PA3 上，否则与 MSP 的 TX 抢线。
  3. 上电时 `MSP_Color_Init()` 只挂一次接收，**USART2 一旦发生 ORE/FE/NE 错误，
     HAL 会停掉 DMA 接收**，而 `usart.c` 的 `HAL_UART_ErrorCallback()` 对 USART2
     **没有任何处理**（恢复代码被注释在 `usart.c:700-703`）→ 出错后永久收不到。
     这也是"先有字节、之后恒 0"的一种可能，排查时值得一并确认。
  4. **数字段 `rgb_raw` 不能拆成三个数** —— 发送端是 `%d%d%d`，无分隔符也无定宽，
     `"2003040"` 是 (200,30,40) 还是 (20,03,040) 无法唯一确定。要程序化用 RGB
     必须先改发送端为 `%03d%03d%03d` 或加分隔符（`msp_color.h` 顶部已注明）。
  5. ⚠ **`MSP_Color_Take()` 会消费 `pending`** —— 挂在 `FC_TASK` 里每周期抢一次帧，
     与 `block_collect.c` 里 `MSP_Color_Vote()` 的取帧**互抢**。跑正式流程前须把
     `FC_TASK` 里的调试调用摘掉，否则采集侧取不到票、颜色恒走兜底表。

#### V1.27.0 - 2026-10-07
- **修改类型**：修改（**物块摆放：识别兜底 + 漏料不卡流程**）
- **涉及模块**：
  - 业务层 / `app/ColorIdentif.c`、`.h`（新增 `TT_BlocksCoverTable()`；改 `TT_SeekBlock()`）
  - 业务层 / `app/block_collect.c`（采集循环不再错位；新增 `block_fill_defaults()`）
- **修改内容**：

  **现象**：识别不可信时四个物块只出去两个；**漏一个物块之后，剩下的也全不放**。

  **根因（三条独立，都在"收集 → 摆放"这条链上）**：

  ① **形状基本恒判 `SHAPE_RECT`** —— `block_basic.c:163` 的阈值表
     `Slot_Shape[] = {640,641,637,641}` 与实测 `raw` 不重叠（V1.26.6 备注已点明）。
     四个槽于是出现**重复的** `(颜色,形状)` 组合，而 `TT_SeekBlock()` 是**按组合逐个
     搜槽**的，`T1[4][2]` 要的两组 `CYLINDER` 无人匹配 → 那几个物块永远放不出去。

  ② **`TT_SeekBlock()` 搜不到时游标不推进** —— 原来直接 `return 0`，`s_seek_slot`
     停在原地，下一次 `FindCircle` 又从头搜**同一个**组合。而 `NF_STAGES` 给的是固定
     `{Event_FindCircle, 5u}` —— 一个组合匹配不上就把**后面所有轮次**全吃掉。
     这是"漏料之后剩下的全不放"的直接原因。

  ③ **漏料时 `continue` 把转盘推进一起跳掉** —— IR 超时走 `continue`，连
     `BlockBasic_TurntableTo(slot+1)` 都没执行，转盘停在上一槽，之后所有槽
     **错位一位**（夹的是上一槽的位置、记的却是下一槽的号）。收集结果整批被污染，
     又回头加剧 ①。

  **修法**：

  - `TT_SeekBlock()`：搜完 `s = 1..4` 仍未命中时，**先 `s_seek_slot++` 再 `return 0`**。
    语义由"搜到为止"改成"每轮推进一行" —— `T1[]` 是逐轮推进的表，不是重试队列。
    首轮 `s_seek_slot == 0 → return 1`（黄锥槽）的分支未动。
  - `TT_BlocksCoverTable()`（新增）：遍历 `T1` 每行，看是否存在**已采集**且
    `color/shape` 与之相等的槽下标 `1..4`；任意一行找不到即 `false`。
    `T1` 四行组合互不相同，故"四行都能找到"等价于"四个槽与四行一一对应"。
    `T1` 行数提为 `#define T1_ROWS`，替换散落的字面量 `4u`。
  - `block_fill_defaults()`（新增，`block_collect.c`）：采集 `for` 循环之后调用，
    与奖杯分支末尾的 `trophy_fill_missing()` 同一位置、同一思路。组合齐全则一个槽
    都不动；不齐就按槽序**只对已采集的槽**依次写入（红方 / 红圆 / 蓝方 / 蓝圆），
    并逐槽打日志。**漏料槽不写**，保持 `TT_Init()` 后的 `(0,0)`，`TT_SeekBlock()`
    自然搜不到它 —— 少来几个物块就只摆几件。
  - 采集循环：把"转盘推进 / 关门"移出 `if`，**不管漏没漏料都执行**；
    `osDelay + GripperClamp + identify_slot` 只在实际等到物块时做；删掉 `continue`。

  **取舍（用户选定）**：兜底范围 = **整批覆盖已采集的槽**（不逐个猜"哪个槽错"）；
  漏料槽 = **跳过、不跑去空槽空放**。

- **影响范围**：物料采集的 `g_tt` 内容与摆放阶段的槽位匹配。奖杯分支未动
  （`trophy_fill_missing()` 与 `TT_SeekBlock()` 无关）。接口为**兼容新增**
  （只加 `TT_BlocksCoverTable()`，未改任何已有签名）。
- **验证状态**：编译已验证（`--clean-first`，147/147，无 error、**无新增告警**；
  既有告警仍是 `app_freertos.c` 的 `test` 未使用 + `oled_data.c` 的 4 处
  missing-braces）。**实机未验证**。
- **备注**：
  1. **未重标 `Slot_Shape[]`** —— 需要现场实测的 `raw` 数据，本次不动；
     默认表兜底已经绕开了它。形状那一维要真正可用仍须重标（V1.26.6 备注）。
  2. **未改 `NF_Stage_FindCircle()` 的时序** —— 现在仍是"先等找圆 `g_circle_dir=='O'`
     再 `TT_RotateByQR()`"，所以"找不到"的那一轮仍会**白等一次
     `NF_CIRCLE_TIMEOUT_MS`（60s）**。改成先查摆放表再等找圆能省下这 60s，
     但会动到找圆时序，留作单独一次改动。
  3. **上机怎么确认**：
     - 识别不可信的轮 → 看 `[COLLECT] (颜色,形状) 凑不齐 -> 已采集的槽整批走默认表`
       与随后的 4 行 `slot N -> default ...`；5 轮 FindCircle 应打**5 个不同的**物理槽
       （1 锥 + 2/3/4/5 各一次），且不再出现"该 (颜色,形状) 在 g_tt 里找不到"。
     - 故意漏一个物块 → `slot N: no block, skip` 只出现一次且**后面各槽的
       `slot=..raw=..` 仍对得上**（不再错位）；"找不到"**最多出现一次**，
       剩下的 3 件仍全部摆出去。

#### V1.27.1 - 2026-10-07
- **修改类型**：修复（**颜色投票：一帧 = 一票**）
- **涉及模块**：硬件驱动层 / `hardware/sensors/msp_color.c`、`.h`
- **修改内容**：

  **问题**：`MSP_Color_Vote()` 名义上是"窗口内收到的帧全部计入票"，但实际是
  **每 10ms 顶多数一票** —— 同一批连着到的几帧被并成一票。

  **根因**：票是拿 `s_msp.pending` 数的，而它是**灯不是计数器**
  （`msp_color.c` 的 ISR `MSP_RX_COLOR` 分支只写 `pending = 1u`）。一个 10ms
  窗口里到了 3 帧，ISR 置灯 3 次、`color` 覆盖 3 次，`MSP_Color_Take()` 每次只取走
  **最后一帧** → 前面两帧的票凭空消失。"一帧 = 一票"就是从这儿断的。

  **修法**：票改在 **ISR 里按颜色分别记**，`MSP_Color_Vote()` 只负责"读并清"。

  - `s_msp` 加两个票箱 `volatile uint16_t ok_red / ok_blue`（ISR 写、任务读）。
  - ISR 的 `MSP_RX_COLOR` 分支：颜色字符在 ISR 里本来就知道，`'r'` 就 `ok_red++`、
    `'b'` 就 `ok_blue++`。`pending` **保留不动** —— 仍给 `MSP_Color_Take()`（调试打印）
    和 `MSP_Color_Wait()`（单帧等待）用，投票与它们解耦。
  - `MSP_Color_Vote()`：**开窗时清零票箱**、窗口结束读票并清，中间的
    `while (MSP_Color_Take(&c))` 整段删除。

  **取舍**：开窗清零，即**只算本窗口内**的帧 —— 这与 V1.26.7 特意做的
  "不预先丢残留帧"**相反**。理由：票箱改成计数器后，"手上那帧"变成了
  "上次 `identify_slot` 以来的**全部**帧"，其中大部分是转盘转动过程中扫到的旧槽；
  而每帧一票之后窗口内票数远多于从前（从前每 10ms 顶多 1 票），"票不够"这个
  前提本身已经不成立。
  ⚠ 另有一个**无关**的既存项未动：`MSP_Color_Wait()` 从头到尾**没有调用者**
  （V1.26.7 起被 `MSP_Color_Vote()` 取代），按第 5.3 节保留不删。

- **影响范围**：物料采集的取色。每槽 600ms 窗口内的票数会明显多于从前，
  多数判定更稳；`MSP_COLOR_VOTE_MS` 这个初值可能要**重新评估**（票多了之后
  可能不需要这么长的窗口）。奖杯分支不受影响。
- **验证状态**：编译已验证（`--clean-first`，147/147，无 error、**无新增告警**）。
  **实机未验证**。
- **备注**：
  1. **别再拿 `[MSP] color='x'` 的行数当票数** —— 那条是 `MSP_Color_Take()` 打的，
     一个 10ms 窗口里连到的几帧只会打印**最后**一帧，**必然比真实票数少**。
     票数以 `MSP_Color_Vote()` 自己打的 `[MSP] color votes: r=.. b=..` 那行为准
     （`.h` 里 `MSP_COLOR_VOTE_MS` 的注释已改正）。
  2. 开窗清零/读票是**任务侧**、自增是**ISR 侧**，严格说有一拍竞态：极少数情况下
     开窗那一瞬间到的帧会被漏掉或多算。窗口几百 ms、取的是多数，对结果无影响。
  3. 顺带修掉一条**本次改动之外**的新告警：`MSP_Color_DebugPoll()` 里的
     `printf` 被注释掉后 `buf` 无人使用（`-Wunused-but-set-variable`），
     加 `(void)buf;` 压掉，**注释那行原样保留**，要恢复打印只需取消注释。
